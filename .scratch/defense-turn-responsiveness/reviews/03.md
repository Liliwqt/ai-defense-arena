# Ticket 03 review — bounded processing and transient retry

Scope: ticket 03 implementation relative to ticket 02 baseline `c31cf8f`.
Frozen candidate: `/tmp/opencode/turn03-review`; baseline:

## Spec review

An independent read-only Spec review confirmed the revised candidate:
the interaction deadline starts at answer/probe submission, carries through
interpretation into the following question, survives resume/reconnect, and does
not restart at a stage boundary. The transient-retry budget is shared across
those stages; legacy keeps its question retry without an interpretation
auto-retry; Free remains windowless; manual recovery starts a fresh bounded
attempt without changing the answer clock or charge; expiry discards late
results and retains pending work.

The earlier findings were corrected:

- P0: the 45-second window previously restarted at interpretation→question and
  started only when the worker ran. It now starts in `SubmitAnswer` /
  non-direct `SubmitProbeReply`, is stored on `Room`, and is consumed by both
  interpretation and question operations.
- P1: baseline legacy question retries were restored while legacy
  interpretation and provider-directed 429 retries remain disabled.
- P2: `resume_operation` now retains `retrying=True` for an admitted second
  attempt, so question and interpretation waiting labels show “Trying again…”.
- P2: controlled-clock coverage now includes the shared answer→question window,
  queue delay without a reset, backoff crossing expiry, and the shared retry
  budget across stages.

Remaining review gaps, intentionally left open:

- Real local PostgreSQL spending/concurrency/hold checks could not run.
- The checkpoint-1 runnable status/recovery presentation and measured baseline
  capability are not part of this implementation handoff.
- The reviewer noted that applying the bounded window to openings/first
  questions is broader than the answer-to-next-question example. It was retained
  because the ticket says “new Standard interactive work”; product confirmation
  is still appropriate.
- `retry_after_max_ms=10_000` and `default_backoff_ms=1_000` are provisional
  policy values exposed in snapshots, not measured provider conclusions.
  Ticket 08 owns that measurement.

## Standards review

No documented hard-standard violation was reported. Judgement-level notes:
bounded request code is duplicated between question and interpretation; the
shared retry counter is now incremented on both transient paths; `retrying`
means “this operation has retried” rather than only “waiting between tries”;
and the label-prefix helper is duplicated. The first is retained for now; the
second and the snapshot type were tightened. The candidate is not claimed as a
separate Standards sign-off beyond this report.
