This is a specification for future implementation. All nine interview decisions and the consolidated scope were confirmed by the user. Publication here means publication to the local Markdown tracker, not GitHub or the hosted service.

## Problem Statement

Researchers across disciplines need practice questions appropriate to their actual study. The existing four research reviewers provide useful perspectives, but their broad guidance can overemphasize empirical experiments, human participants or practical beneficiaries. A qualitative interview study, theoretical paper and engineering experiment should not receive the same assumptions about methods, ethics or impact.

The host currently cannot review the panel's interpretation of the research field and approach before starting. Independent interpretation across questions, clarification and coaching can produce inconsistent advice. An ambiguous or interdisciplinary paper should retain its uncertainty and multiple perspectives, while a host correction must not be mistaken for something demonstrated by the uploaded paper.

## Solution

Keep the four research reviewer seats and adapt their perspectives using one shared, host-confirmed research profile for Research paper and Research + code defenses. Code project defenses retain their current behavior.

The existing Prepare defense request suggests the profile alongside the source-grounded coverage map. The profile includes editable research fields and study approaches, an optional setting, and a short explanation with grounded citations and explicit uncertainties. The host reviews it before confirming the map and question budget. Teammates can inspect it without editing it.

A correction requires preparing the map again and reconfirming the budget. An unclear classification may be explicitly confirmed without inventing a method. Multiple fields and approaches may coexist when appropriate. The confirmed profile remains fixed during a defense run and informs all questioning, reactions, clarification, answer probes and coaching. The uploaded material remains the evidence; host descriptions are separately attributed context.

Deliver two runnable local checkpoints: profile/map review, then consistent reviewer adaptation. Mirror the experience in React and Streamlit and present the local preview before publication.

## Implementation Decisions

1. **Scope and stable identities.** Apply the profile only to research and mixed defenses. Preserve Methodology Reviewer, Ethics Reviewer, Impact Reviewer and the existing internal Critical identity, displayed as Critical Reviewer. Preserve the four opening turns and subsequent coverage-driven selection. Do not create seats, rename protocol identities or change code-only roles.
2. **Profile contract.** Introduce a validated research-profile value containing a bounded, nonempty collection of research-field labels and a nonempty collection of approach choices, optional setting, a concise source explanation, grounded paper references and explicit uncertainties. Allow multiple fields and approaches. Approach choices are quantitative, qualitative, mixed-methods, theoretical, computational/design, other and unclear. Use the existing text/citation validation conventions; reject invalid types, oversized values, unsupported choices and invalid locations instead of truncating or trusting them.
3. **Classification is a lens.** These broad choices are not an exhaustive research taxonomy. Multiple approaches do not automatically prove a mixed-methods design. Preserve uncertainty and differences between documents or sections rather than flattening them into a single unsupported classification. Topic objectives and references determine which aspect is relevant.
4. **Source and host provenance.** Keep the source-grounded AI explanation distinguishable from host-edited descriptions. Host corrections are authoritative about the requested practice lens, not about what the paper demonstrates. Remapping receives corrections as attributed data and retains them; it may identify supported discrepancies or uncertainty without silently replacing the correction. Reviewers cite actual uploaded evidence and ask about material discrepancies rather than asserting that either a label or a quotation proves a method is valid.
5. **One planning request.** Extend the existing structured map response to include the profile. It receives all accepted paper text, selected research stage, accompanying code in mixed mode and any saved corrections. Do not add a classification or evaluator request. Each explicitly requested reprepare is another ordinary mapping request under existing access and AI-work limits.
6. **Grounding and partial progress.** Resolve every displayed supporting quote from server-owned extracted text and validate its document location using existing citation handling. Paper references support classification; code can support mixed-mode topic connections but cannot replace the paper's basis. An uncertain classification remains explicitly uncertain rather than claiming missing information is absent from all research. Streamed topics remain Draft; no provisional profile is represented as validated or host-confirmed. Preserve the existing mapping activity feed without exposing private AI reasoning or fabricated confidence, completion percentages or reading claims.
7. **Host commands and map identity.** Extend the existing authenticated host-only preparation/approval command flow to carry validated correction input and explicit profile confirmation. Confirmation binds to the current map identity, including its profile and question budget. The server derives ownership from verified authority. Guests may inspect snapshots but cannot edit, prepare, retry or approve. Reject stale map identities, ambiguous approval and client attempts to substitute an unvalidated profile.
8. **Correction and readiness.** Any accepted profile correction invalidates the old approval and Start eligibility and requires remapping before renewed confirmation. Retain uploads and corrections throughout preparing, failure and retry. A successful reprepare creates a new map identity and requires review of its resulting profile and renewed budget confirmation. Local unsaved changes must also prevent the host interface from presenting the prior approval as ready to start. Invalid commands must not destroy the current valid state.
9. **Uncertainty confirmation.** Allow Unclear with an explicit host acknowledgment. Do not default uncertain profiles into a specific method. The acknowledgment confirms the current scope and uncertainty, not the research's quality or completeness. Failure to classify confidently is distinct from an invalid or unreadable AI response, which remains a preparation failure requiring retry.
10. **Ordering and obsolete work.** Capture profile/correction data immutably with planning inputs and use existing room coordination, revision and generation/run fences. Reject edits during an active run. Reject or invalidate obsolete preparation as appropriate without allowing late progress or final results to replace newer corrections, approval or a newer run. Existing duplicate-work protections remain in force; reconnect and repeated confirmation create no AI request.
11. **Run binding and compatibility.** Research start requires the current validated map, explicitly confirmed profile and approved budget. Older maps without a profile require Prepare defense; do not synthesize one at Start. Capture the confirmed profile in the research session for the run. Restart using an unchanged map retains that profile under the existing explicit cost/access rules. A different profile requires an allowed preparation phase, remapping and new confirmation before a subsequent run; it must not mutate active or previous turns, coverage or coaching. Do not introduce a new room-reset or history-rewrite lifecycle.
12. **Shared request context.** Use one shared profile serializer and adaptation-guidance boundary across mapping, research question generation, reactions, submission interpretation, clarification, answer probes and coaching. Question/progression/coaching context already carries the research session; submission interpretation requires explicit profile propagation in its captured input. Snapshot the same confirmed value for every request, excluding account details and private team chat. Names, source text, profile labels and host descriptions remain data rather than instructions.
13. **Reviewer guidance.** Methodology examines design, feasibility, relevant measures/analysis, qualitative credibility, theoretical reasoning or computational/design evaluation as appropriate. Ethics examines applicable integrity, data, participant and societal risks without inventing participants or approvals. Impact includes contribution to knowledge and practical relevance without requiring commercial benefit. Critical examines the research gap, theoretical basis, evidence, alternatives and limitations. Keep the existing distinct voices and respectful, answer-aware reactions; specialization must not fabricate subject credentials.
14. **Stage and conversation continuity.** Preserve Proposal, Completed study and Let AI infer as a separate research-stage setting. Profile classification must not silently change stage or invent completed results. Preserve direct-question preference, occasional grounded what-if scenes, conditional suggestions, language matching, modern Cebuano preferences, same-question clarification intent, answer probes, transcript retention, timers, voting, question budget and coverage semantics. No extra dialogue request or scripted substantive question is introduced.
15. **Shared interface.** Place profile review alongside the coverage map and budget in the existing preparation surface. Display suggested, confirmed, unclear and correction/remapping states clearly. Hosts edit fields/approaches/setting; the generated source explanation remains grounded, not an editable fabricated excerpt. Provide read-only teammate viewing and restore profile, corrections, uncertainty and confirmation from server snapshots on reconnect. Preserve the current question-centered layout and accessible desktop/portrait/landscape controls.
16. **Streamlit parity.** Mirror mapping, profile editing, uncertainty acknowledgment, remapping, budget confirmation and profile-informed dialogue/coaching in the single-browser fallback. Include profile corrections and confirmed scope in session invalidation so changing them cannot reuse an outdated map, session or coaching. Use the same validators and profile guidance; do not add multiplayer voting or chat.
17. **Access and financial boundaries.** Retain existing account ownership, CSRF, guest-token checks, preparation access checks and run reservation/charge/return rules. Profile preparation/confirmation itself does not start a run or deduct run credits. Preserve existing payment, voucher, provider and local-test-mode implementations and financial architectural decisions. Profile errors must not impersonate a charged run failure or award/return credits.
18. **Two checkpoints.** First deliver validated profile/map review, correction/remapping/confirmation, shared snapshots and reconnect while preserving existing question behavior. Then wire consistent subject-sensitive reviewer guidance through every dialogue/coaching path and Streamlit, and complete integrated local review. Both checkpoints leave the app runnable, identify what is implemented versus pending, and update documentation and the handoff log. The feature is complete only after both checkpoints and the agreed verification.

Use existing fake AI workflows and clock/storage fixtures. 5. **Study cases.** Use synthetic qualitative education interviews, quantitative experiments, theoretical work, computational/design work, interdisciplinary multiple-approach material, ambiguous methods and mixed paper/code sources. 7. **Integrated defenses.** Complete mocked two-client research and mixed runs with clarification, answer probes, voting, timeout, retry, reconnect, transcript and coaching. Verify profile stability and exact citations throughout, appropriate coverage and unchanged budget/timer/access/charging behavior. Include a defense beyond eight turns using the existing adaptive research policy; no new turn count is introduced by profile review.
8. **Offline gate and visual evidence.** Run the existing complete Python and React suites and production build at each completed checkpoint. Review desktop, phone portrait and phone landscape for readable profile labels/explanations, source locations, selection controls, keyboard focus, internal scrolling and unclipped question/dock controls. Present the working local preview and screenshots. Distinguish mocked browser runs, actual live AI, hosted verification and installed-device checks.
9. **Separate live quality review.** With a configured local key, inspect real conversations across representative empirical, theoretical and interdisciplinary papers. Assess subject relevance, concrete answer-aware reactions, useful follow-ups, appropriate Ethics/Impact framing, language continuity, uncertainty and absence of invented claims. Record model, setting and observed outcomes without secrets or private uploaded text. Passing mocks do not substitute for this evidence; publication is a later requested step.

## Out of Scope

- Changing or adding reviewer seats, dynamic protocol role names, code-only defense rules or the four research opening turns.
- Institution-specific defense rubrics, country-specific compliance judgments, ethics certification, fabricated examiner credentials or claims of guaranteed expertise.
- External literature retrieval, automatic checking of every discipline-specific factual assertion, fine-tuning or a separate classification/evaluator service.
- Changes to model/provider selection, reasoning configuration, payment packs, pricing, credit spending, vouchers, authentication or the existing opt-in local testing runner.
- Altering voting, timers, question/answer/probe/clarification semantics, turn budgets, coverage completion, source citation rules or PDF reading behavior.
- New document formats, larger upload limits, OCR, figure/equation interpretation, durable defense history or cross-restart room persistence.
- Broad room-layout redesign, new mobile wrapper capabilities or adding multiplayer voting/chat to Streamlit.
- Implementation during specification synthesis, remote issue publication, committing/pushing, deployment or changes to frozen main/the current live service.

## Further Notes

The research profile is a practice lens, not a research-stage declaration, coverage assessment, credential or proof of study correctness. Server validation can establish schema and excerpt provenance; it cannot establish that the AI's classification or scientific interpretation is correct. The host remains able to confirm uncertainty and explain material discrepancies during the defense.

Rooms remain in memory. A restart loses active rooms; snapshots restore reconnection to a still-existing room, not durable research history. The feature must retain existing service/credit recovery behavior without changing it.

Existing financial ADRs concern payment verification, separate balances and run compensation; this feature preserves those boundaries. No new ADR was required for the confirmed research-profile planning choices. Existing uncommitted reasoning/local-access work and unrelated research notes must be preserved and identified separately during later review.

The first checkpoint is profile/map review, not proof of adaptive dialogue quality. The second completes shared reviewer adaptation and integrated verification. Keep implemented, mocked, live and user-reviewed claims separate in both documentation and handoff notes.
