# Typed Streamlit research defenses

Run from the repository root:

```bash
.venv/bin/python -m streamlit run backend/app.py
```

Configure `OPENROUTER_API_KEY` in the server environment. Research paper and
Research + code use the shared OpenRouter preparation, planner/reviewer,
same-reviewer interaction and progressive coaching clients. `OPENAI_API_KEY`
and `OPENAI_MODEL` do not select or enable these operations. Code-only starts
remain temporarily disabled; retained results remain readable. Voice is not
part of this single-browser fallback.

Mapping stays explicit, followed by profile and question-budget confirmation.
A failed opening retains the prepared session for Retry or End defense. Accepted
answers and typed clarification/probe exchanges remain in that session. Reports
appear inline in bounded sections; retry regenerates only eligible failed
sections and retains ready cards.

The operator's preparation/run ceilings and shared task bounds apply here too.
Preparation has a durable scope for the same browser identity and accepted
material/settings fingerprint. Reopening or retrying does not reset that scope.
A new explicit defense establishes one run scope and fixed model/reasoning
snapshot with protected coaching funds. Later configuration changes do not
replace that snapshot. Requests reserve before dispatch; known usage settles,
and unknown usage retains its bound. An exhausted allowance can stop extra
retries safely. Numeric sizing and actual model support/cost need ticket06's
separate measurements.

Streamlit retains its existing local, single-browser access model: an opaque
session identity owns provider allowance records, not a Google account or credit
balance. A new browser session has a new identity; refreshing after the Streamlit
session is lost does not restore the old defense. The ledger still retains old
reservations. This fallback does not process purchases, defense-credit charges
or credit returns; those remain with the authenticated multiplayer app.

Provider-mocked AppTest walkthroughs establish routing, validation and recovery,
not actual model quality, compatibility, latency or cost. See the local ticket05
review for verification and remaining gates.
